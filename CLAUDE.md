# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Pug Web SDK (`pug-web`) is a browser-side analytics/event-tracking library written in TypeScript. It auto-captures page views, clicks, scrolls, form interactions, and frustration signals (rage clicks, dead clicks), then sends them through a hand-rolled `fetch` transport that speaks the Connect protocol (binary protobuf) to a backend via `BatchCreate` RPCs. The Connect runtime (`@connectrpc/*`) and client-side protobuf validation (`@bufbuild/protovalidate`) were deliberately removed to shrink the published bundle — only `@bufbuild/protobuf` (proto codec/reflection) and `uuidv7` remain as runtime deps.

## Build & Development Commands

```bash
bun install            # Install dependencies
bun run build          # Stamp src/version.ts (prebuild), compile TypeScript to dist/ with tsc, then bundle the CDN IIFE (dist/cdn/) via scripts/build-cdn.mjs
bun run watch          # Watch-mode TypeScript compilation
bun run dev            # Watch TypeScript + serve on port 3000
bun run serve          # Serve static files on port 3000
bun run lint           # Lint & auto-fix with Biome (biome check --write .)
bun run format         # Format source files with Biome (biome format --write .)
bun run typecheck      # Typecheck src + type-level tests (tsc -p tsconfig.typecheck.json)
bun run test           # Run tests once (vitest run)
bun run test:watch     # Run tests in watch mode (vitest)
```

**Manual testing:** After building, run `bun run serve` and open `http://localhost:3000`.

**Automated tests:** Vitest (jsdom environment). Specs live alongside source as `src/*.test.ts`. Run via `bun run test` (single run) or `bun run test:watch` (watch mode). Use `bun run test`, not `bun test` — the latter invokes Bun's built-in test runner instead of Vitest.

**Shared test helpers:** `src/*.test-utils.ts` (`storage-envelope.test-utils.ts`, wrappers over the retention envelope so the storage-asserting suites stop hand-rolling `<expiry>|<value>`; `consent-gate.test-utils.ts`, the `GRANTED`/`DENIED` gate values, so the `as GrantedGate` cast the brand exists to keep rare lives in one place rather than in each of the four suites that drive a gated factory — its only import is `import type`, so it adds no runtime edge to the suites that use `vi.resetModules()`). Excluded from `tsconfig.json` so the build does not compile them (`exclude` only prunes roots — a production module importing one pulls it back in and emits it to `dist/`, so nothing under `src/` outside tests may import them; enforced by `test-utils-imports.test.ts`, which reads every shipped source and fails on such an import), but **included** in `tsconfig.typecheck.json`: vitest transpiles without checking, so that is the only thing typechecking them, and since typecheck is `noEmit` excluding them there bought nothing.

**Type-level tests:** `src/*.test-d.ts` are checked by `bun run typecheck` (and CI, with `exactOptionalPropertyTypes` on — without it `track-types.test-d.ts`'s `scroll: flag || undefined` case pins nothing, and reverting `AutoCaptureSelection` to bare `true` leaves CI green while shipping the regression to consumers on `@tsconfig/strictest`), never run and never emitted — the build's `tsconfig.json` excludes them, and vitest's patterns do not match them. They exist for assertions no runtime test can make: that some code **fails** to compile. Each `@ts-expect-error` is the guard, and it fails in the right direction — if the expected error stops happening, tsc reports the unused directive as an error (TS2578). `src/track-types.test-d.ts` pins `TrackFn`'s behavior this way; reverting it to overloads makes two directives unused and fails CI. `src/event-identity.test-d.ts` pins `EventIdentity` the same way: removing the `?: never` members makes four directives unused, one per spelling of "cookieless event carrying identity" (literal, spread, variable, pre-built object) — all four of which compiled before, and none of which any runtime test can observe, since the failure being guarded is a *missing* compile error. `src/before-send-types.test-d.ts` pins `BeforeSendFn`/`BeforeSendEvent`: that the README's masking and `delete` idioms compile (they did not — the bags were typed `PropValue`), that reassigning a bag or `kind` does not, and that the return type stays `| void` rather than `| undefined` — a block-bodied arrow with no return infers `void`, so the documented in-place idiom stops compiling under `| undefined` while nothing at runtime can tell the two apart. `src/init-options.test-d.ts` pins the `| undefined` spelling of every optional member of `InitOptions`/`TrackingConsentConfig`/`SessionConfig`: a config builder holds optionals as `T | undefined`, and under `exactOptionalPropertyTypes` that spelling was a TS2375 for exactly the population (CMP-assembled privacy configs) the options exist for — the same reasoning as `AutoCaptureSelection`'s `true | undefined`, now applied surface-wide. `src/consent-gate.test-d.ts` pins the `ConsentGate` brands: a bare `() => boolean` satisfies neither gate (both laundering spellings — annotation and wrapper arrow) and the two gates are mutually unassignable; reverting `__gate` to optional makes the laundering directives unused (TS2578) while nothing else in the build fails, which is the silent-revert shape every file in this list exists to close. It also pins the *arity* of all three gated factories (`configureProfile`, `configureSession`, `createCookieLayer`): all three throw a `TypeError` at the head on a non-function gate — uniform fail-loud for the untyped callers typecheck never sees, each pinned in its own runtime suite — so for typed code omission must be a compile error, and reverting any one parameter to optional changes no runtime behavior (the guard throws regardless of the typing), so nothing else in the build objects — which is what these directives close: they go unused, and TS2578 fails the build.

## Architecture

### Core (`src/pug.ts`)

`pug.ts` exports `init(projectId, options)`, `track(kind, props?, opts?)`, `identify(externalId, traits?)`, `reset()`, `destroy()`, `setAutoCapture(selection)`, `setTrackingConsent(state)`, `optInTracking()`, `optOutTracking()`, `isTrackingEnabled()`, `getTrackingConsent()`, and `isConsentPending()`. `track()` dispatches on consent as an **allow-list** (`granted` → ids, `cookieless` → identity-free, `denied` → drop, anything else → drop + `unreachable(consent)`), not as a deny-check: written the latter way an unhandled state fell through to the full-identity arm, so a fourth state would silently get full tracking plus persisted identifiers with neither the compiler nor the suite objecting. `unreachable` is a non-throwing `(_: never) => void` — not because a throw could escape (the call is inside `track()`'s own try/catch, which would swallow it) but because the `else` branch already logs the offending state by name, and throwing would replace that with a generic message. Widening `TrackingConsent` is a `TS2345` at the dispatch — the one place that must decide. In cookieless consent (`getConsent() === 'cookieless'`) `track()` skips `resolveSessionId()`/`resolveDistinctId()` entirely and builds the event via `toEvent`'s `{ cookieless: true }` identity arm (`EventIdentity` union in `track.ts` — "cookieless with ids" is unrepresentable, enforced by `?: never` members and pinned by `event-identity.test-d.ts`); `identify()` warns once per `init()` and drops. A single nullable module-scoped `state` object (`{ config, transport, apiKey, dryRun, autoCapture, trackingConsent } | null`) enforces single initialization. `init()` builds the shared `PersistentStore` (from `crossSubdomainTracking`, default `false`, and `maxAgeDays`, default 365 — see Cross-Subdomain Persistence) and passes it to `configureSession`, `configureProfile`, and `createTrackingConsent` (the tracking-consent controller is created before `configureProfile` so the latter's init-time identity-cookie expiry refresh can be gated on `isGranted` — no identity write while consent is denied); creates the batched transport (which internally creates the RPC transport); creates the auto-capture controller (the auto-capture controller owns the desired selection and gates listeners on consent via an injected `isTracking` getter, so listeners run in cookieless mode too); and applies the selection with `setDesired()`. `trackingConsent` sets the initial consent and optional persistence (`'granted'`/`'cookieless'`/`'denied'`, or `{ initial?, onReject?, persist?, respectGpc? }` — named `initial` because `default` is a reserved word and could not be destructured), **defaulting to `'cookieless'`**: an install that never configures consent collects events but writes no identifier before the user has answered, so the worst an unconfigured install can do is collect too little (pinned by the first case in `cookieless-storage.test.ts`, which asserts a bare `init()` writes nothing to the device at all); while denied, automatic listeners stay off, `track()` and `identify()` drop calls at debug level, and no events are queued. When the resolved initial consent is not `'granted'`, `init()` **always** purges the queued events (`transport.purgeQueue({ send: false })` — see Batching Layer for why consent teardowns do not transmit) and, **when `isAuthoritative()`**, runs the same identity purge `setTrackingConsent` does. The two are branches, not a purge plus a conditional second one: `purgePersistedIdentity()` drops the queue as its own first step, so calling both made one fault report three times. The two are split deliberately: the queue is an outbound buffer, not an identifier anything reads back, so purging it can never mint a new identity and `isAuthoritative()`'s reasoning does not transfer to it. Folding them together left a prior consented visit's identified payloads on the device through every non-authoritative non-granted init (any config omitting `persist: true` — a bare `'denied'`/`'cookieless'` string, or the `{ initial, persist: false }` form in `examples/cdn/index.html`), to be transmitted on the next pagehide while consent read `'denied'` and re-persisted while it read `'cookieless'`, so entering a non-granted state via config and via transition converge — otherwise a visitor whose CMP now says "reject" would keep a prior consented visit's 365-day identifiers, and the documented "granting later mints a fresh identity" would be false (a later grant would resolve the *pre-existing* session and anonymous ID). `isAuthoritative()` requires a GPC-resolved state **or** both `persist: true` and that the value actually came back from storage (the full formula and its reasoning live in Tracking Consent); neither half of the storage conjunct is optional. Without persistence the initial value is the integrator's pre-banner placeholder (typically a static `'denied'` corrected by a later `optInTracking()`), so purging on it would mint a new identity on every page load. And `persist` alone is not enough either, because nothing is written until an explicit `set()`: on a site adding `{ initial: 'denied', persist: true }` to an existing deployment, every returning visitor's first load finds an empty consent key, falls back to the seed, and would purge identity those users never asked to have deleted — once, for the whole user base, on deploy day. The storage half is pinned by a test in `cookieless-storage.test.ts`; the `persist` conjunct is **redundant** given it (`store` is null unless `persist`, and `restoredFromStorage` is only set inside `if (store)`, so `restoredFromStorage → persist`) and is kept to state the invariant locally rather than rely on that derivation — no test can distinguish it, and dropping it leaves the suite green. With `persist: true` the choice is stored through the shared `PersistentStore` (riding the cross-subdomain cookie when active, otherwise `localStorage`) and restored on the next `init()`; otherwise consent is in-memory and callers pass the initial value on each `init()`. `reset()` returns a **boolean** and performs a full identity discard: `resetIdentity()` (also boolean, so a failed persist reaches the caller rather than only the console), `transport.purgeQueue({ send: true })` (one best-effort beacon, then both queues off the device — `send: true` only here, since a logout leaves consent untouched — on a shared device the next user must not inherit the previous one's queued events, whose `distinctId` is their `externalId` after `identify()`), and `clearProfile()`. `optOutTracking()` applies `getRejectState()` and re-reconciles — tearing listeners down under the default `'denied'`, but **leaving them attached** under `onReject: 'cookieless'`, where events keep flowing without identity — and tears down persisted identity (`clearProfile()` + `clearSession()`, plus the queue drop when the transition reduces consent — see the `dropQueue` predicate in Tracking Consent; an already-cookieless session re-asserting `'cookieless'` keeps its identity-free queue) so no identifiers linger for a user who opted out — in cross-subdomain mode this clears the shared cookie so the opt-out propagates to sibling subdomains, while the persisted consent itself is kept (device-level); `optInTracking()` re-reconciles, restoring the stored selection (a fresh identity is created lazily on the next event) and re-arms the tab registry via `onConsentGranted()`. `setTrackingConsent`/`optInTracking`/`optOutTracking` return a **boolean** — false when the state was unrecognized (consent then fails closed to `'denied'`), the choice could not be persisted, or an identifier could not be removed; after `init()` the state is always applied in memory when valid, so false never means "nothing happened". Before `init()` it does: all three warn and return false having applied nothing — the one case where false really is "ignored", and a banner racing initialization is the likeliest way to hit it. `track()` calls `resolveSessionId()` from `session.ts` on every allowed **non-cookieless** event (the cookieless arm skips both identity resolvers entirely), uses `toEvent()` from `track.ts` to build a protobuf `Event`, and sends it through the transport with a centralized try/catch for error safety. `init()` also warns when `endpoint` is neither https nor localhost (events would cross the network in the clear) and gates `initUserAgentData()` on `isTracking()`, so high-entropy client hints are not requested for a user who is not being tracked; `setTrackingConsent` re-warms them when a transition starts tracking — gated on the transition, not called on every consent change, because `initUserAgentData()` clears the hint cache synchronously and refills it asynchronously, so a CMP re-asserting its state (or `optOutTracking()` under `onReject: 'cookieless'`, where `isTracking()` stays true) would drop `$osVersion`/`$device` from every event until the new request resolved. `destroy()` invokes active tracker cleanup functions through the auto-capture controller, calls `transport.destroy()`, `destroySession()`, `destroyProfile()`, and resets state to allow re-initialization; it releases runtime resources without clearing persisted identity (that is `reset()`'s job), so a subsequent `init()` resumes the same session and profile.

### Auto-Capture (`src/auto-capture.ts`)

Owns SDK automatic listener selection and lifecycle. `autoCapture` supports `true`/`false` or an `AutoCaptureSelection` object; object mode is an allowlist, so only keys set to `true` are enabled and omitted keys stay off. `AutoCaptureSelection`'s values are typed `true` rather than `boolean` so the denylist misreading (`{ scroll: false }` — which reads as "everything except scroll" but under an allowlist enables nothing) is a compile error rather than a silent loss of all capture; a runtime value known only at call time is written `scroll: flag || undefined`. Resolution and diagnostics are split: `resolveAutoCapture` is pure and runs on every reconcile, while `validateAutoCapture` owns every warning and is called from `setDesired` — deliberately not from `reconcile`, which only consults the selection while tracking is active (granted or cookieless), so validating there said nothing at all for the consent-first flows the README recommends (the diagnosis arrived at `optInTracking()` time, in a user's browser) and then re-warned on every consent cycle. Both treat the value as untrusted (the CDN one-tag install feeds it from `data-options` JSON). The allowlist warning fires on either spelling of the misreading, because each loses capture the integrator believes they kept: an explicit `false` anywhere (reported even when the selection still enables something — `{ pageView: true, scroll: false }` keeps page views, so a check keyed only on a zero enabled count stays silent while click, form, rageClick and deadClick are lost), **or** a selection that names trackers but enables none, which is what a non-`true` value (`{ scroll: 'true' }` from a template, `{ scroll: 1 }` from a config store) or a misspelled key produces — there the `invalidKeys`/`unknownKeys` warning names the offending key but reads as "we ignored that one", understating a total loss. Either way the message names what the selection actually enables, since that is what reveals the loss. Both are keyed on a *written-out* value, not on key count, so `{}` and the documented `scroll: flag || undefined` idiom (with the flag false) stay silent: they embed no misconception. `AutoCaptureSelection`'s values are `true | undefined` rather than bare `true` so that idiom also compiles under `exactOptionalPropertyTypes`, which ships in `@tsconfig/strictest`; the `| undefined` weakens nothing, since `false` and a `boolean`-typed value are still rejected. `src/track-types.test-d.ts` pins the compile-time half — `pug.test.ts` reaches those shapes through `as never` casts, so reverting the values to `boolean` would otherwise leave the whole suite green. Runtime tracker cleanup is owned per tracker in a controller-local `Map`, allowing `setAutoCapture()` to add/remove SDK-owned listeners after init without bloating `pug.ts`.

### Cross-Subdomain Persistence (`src/cookie.ts`, `src/persistence.ts`)

Identity is shared across subdomains by mirroring it into a first-party cookie on the registrable domain. **Off by default** (`crossSubdomainTracking` defaults to `false`): cross-subdomain identity relaxes browser same-origin isolation to the weaker same-site model, so per `docs/cross-domain-tracking-threat-model.md` §7 (in the backend `pug` repo, not this one) it is an explicit per-integrator opt-in, never inferred. `createCookieLayer(config, isGranted, doc?)` in `cookie.ts` takes `CrossSubdomainConfig` (`boolean | { domain }`): `false` (the default) returns `null` (no cookie layer, origin-scoped `localStorage` only); `true` (explicit opt-in) discovers the widest settable domain (eTLD+1) via `seekRegistrableDomain()` — a write-probe that tries `domain=.<candidate>` widest-first and takes the first cookie the browser accepts, so public suffixes (`.com`, `.co.uk`) are rejected by the browser itself with no bundled suffix list; `{ domain }` pins an explicit domain (verified with a probe; on rejection or host mismatch it warns and falls back to host-only). `domain` is **required** in the object arm, since an all-optional one made `{}` legal and `{}` would otherwise infer the opt-in this section says is never inferred (a config builder spreading unset optionals produces exactly that). Pinned by `cross-subdomain-types.test-d.ts`, where the `maxAgeDays` case must carry a `domain` (`{ domain: 'acme.com', maxAgeDays: 180 }`): as a bare `{ maxAgeDays: 180 }` it errored only for the missing `domain`, exactly as the `{}` case above it, so re-adding `maxAgeDays` to the object arm typechecked clean. The literal pin alone closed nothing for a config builder holding the old shape in a variable or spreading it (excess-property checks guard only fresh literals), so the arm also carries `maxAgeDays?: never` — the `EventIdentity` pattern — pinned in both forms; and when a pinned object still carries extra keys with defined values, `resolveIntent` warns instead of silently swapping the old shape's deliberately shortened lifetime for the 365-day default (keys holding `undefined` are exempt — a builder spreading an unset legacy optional produces `{ domain, maxAgeDays: undefined }`, which configures nothing). The type is only half of it: `resolveIntent` enforces the same rule **at runtime**, because the one-tag install supplies this as untyped `data-options` JSON that no compiler ever sees. Only a literal `true` reaches `seekRegistrableDomain()`; an object must carry a non-empty string `domain`, and every other shape resolves to off with a warning. Three of those shapes are reachable in practice and all three used to auto-discover: `{}` (the spread-optionals case), `{ maxAgeDays: 30 }` left behind by an upgrade from the removed lifetime arm — the *documented* old behavior for an object without `domain` — and a stringly-typed `"true"`/`"false"` out of an HTML template, where a truthy non-object fell through to the probe and `"false"` therefore **enabled** cross-subdomain identity. Covered by `cookie.test.ts`. Cookie lifetime is **not** configured here: it moved to the top-level `maxAgeDays` (see Retention below), which bounds `localStorage` too — the nested option bounded only the cookie, which is the layer the default install does not even use. Host-only (empty domain attribute) is also used on localhost and IP hosts; PSL-listed multi-tenant PaaS hosts (herokuapp.com, vercel.app, …) need no special-casing, since their shared suffix is a public suffix the browser rejects, so the widest-first probe lands on the tenant's own host. **Not covered:** a custom multi-tenant registrable domain *not* on the Public Suffix List (e.g. `a.myplatform.com` / `b.myplatform.com` as separate tenants) — the probe accepts `.myplatform.com` and sibling tenants can read each other's identity (threat model T2/T3); there is no bundled denylist backstop, so such deployments must pass an explicit `{ domain }`. The public API JSDoc warns integrators of this. Cookies are written as `<key>=<encodeURIComponent(value)>; SameSite=Lax; path=/[; domain=.X][; secure]; max-age=<caller's remaining TTL>` — `set(name, value, maxAgeSeconds)` takes the lifetime per call so the cookie expires with the value it holds; the parameter is **required** and no write site in the module defaults it, since a defaulted one would silently give a cookie a lifetime nobody chose — capped at 3800 chars (warn + skip), with read-back verification. `set`'s `value` parameter is the branded `StoredEnvelope` (see Utilities) — the layer stores only enveloped strings. In cross-subdomain mode both `get()` and `set()` reconcile a stale host-only twin on first access per key (`reconcileTwin`): the twin is expired so it can neither shadow the shared cookie on reads nor — via a read-then-refresh (`getAnonymousId`, session activity) — be promoted onto the shared cookie and corrupt identity site-wide; if expiring it leaves nothing, the twin was the sole value (a host-only → shared migration) and is re-promoted to the shared cookie so siblings inherit it — with **its own remaining TTL**, read back out of the envelope it carries (`twinLifetime`). A flat 365d there would outlive the value's contents and ignore a lowered `maxAgeDays` on the one path that widens a cookie's scope. A twin that does not decode predates the envelope and is **never promoted** — that would widen an identifier nothing can ever expire — but it is **restored host-only rather than discarded**, because what an undecodable value means is the store's call: it removes one on sight, and `getItemOrLegacy` hands the consent record's bare value up first. Destroyed by this layer, that read saw nothing and, in cross-subdomain mode, the resulting cookie miss also swept the localStorage mirror — so a refusal recorded by a pre-envelope build reverted to the config seed with nothing logged, defeating the adoption hook on the one mode it was never tested in. `twinLifetime` returns `'undecodable'` and `'expired'` separately for this reason: collapsed into one `null`, "retention says drop this" was applied to "this layer cannot read it". A promotion that fails restores the twin — with its host-only attributes (`SameSite=Lax`, `secure` on https: a bare write handed a previously-Secure identity cookie to plain http) and read-back verification, warning when the restore is lost too, since the expired twin was the sole copy. The same restore covers the other consumer of a preserved twin: a later `set()` expires it ahead of read-back (created first, it would otherwise win the scan and fail a landed write), and if the replacement write then does not land — by read-back mismatch *or* by throwing, two separate arms each pinned in `cookie.test.ts` — the twin is put back rather than left destroyed, the reachable case being the consent record's restore write, whose loss reverted a recorded refusal to the config seed. `preservedTwins` carries the twin's **value only**; the lifetime is recomputed from its own envelope (`restoreConsumedTwin`) at restore time, because a TTL captured when the twin was first preserved goes stale on a long-lived page — replayed, a twin preserved with `R` seconds left and restored at `R−10` was written back with a fresh `max-age=R`, outliving the deadline stamped in the value it carries. A twin whose retention ended meanwhile is deliberately not restored: the expiry already removed it, which is what its deadline asks for. `remove()` clears the registration too, but only on a **confirmed** removal — left behind, it outlived the teardown and the failed-write arm restored an `identify()`ed email *after* `optOutTracking()` reported success (pinned). A reconciliation that *throws* un-latches the key (`reconciledKeys.delete`) so the next access retries, warning once per key — latched as done, a stale twin kept shadowing the shared cookie for the whole page load with only a debug trace no default install can see. `createCookieLayer` takes a required `GrantedGate` ahead of `doc` (minted by `deferredGrantedGate` in `tracking-consent.ts`, so the `as GrantedGate` cast stays out of shipped code beyond the brand's module — `consent-gate.test-utils.ts` holds the one test-side mint, `test-utils-imports.test.ts` fails the suite on any shipped import of a test-utils file, and `consent-gate-containment.test.ts` fails it on any `as GrantedGate`/`as TrackingGate`/`__gate` in a shipped module other than `tracking-consent.ts` — without which a module minting its own gate typechecked, passed every runtime suite and bypassed the consent system silently. Containment by those two specs, not a compiler guarantee, since the phantom member is a plain property a deliberate `Object.assign` can mint — no brand prevents that, and this one exists to catch accidental swaps — written inline in `init()` it is indistinguishable from the wrapper-arrow laundering `consent-gate.test-d.ts` rejects; it is late-bound because the controller needs the store and the store needs the layer, and it resolves to **not granted** until the controller exists, so no fail-open default survives anywhere in the gate chain — which costs nothing, since the only value read in that window is the consent record and the sole thing a withheld gate suppresses is the twin *promotion*, the twin itself being preserved and read normally), and `reconcileTwin` gates **only the promotion**, putting the twin back at its host-only scope, latched for the page — a mid-page grant migrates on the next page load; un-latched, every later read repeated the delete-and-restore, an identity Set-Cookie on the read path in the state that promises no device writes (measured at 10 writes across 5 reads before the latch; `cookie.test.ts` pins the latched behavior at 2 — one expire plus one restore). Everything before the promotion is a *deletion* — expiring a stale twin so it cannot shadow the shared cookie — which no consent state forbids and which `configureProfile` depends on, since it reads `external_id` once and latches the result for the page; gating the whole reconciliation instead let a stale twin win that read and become the `distinctId` after a mid-page grant. The reason the promotion needs a gate at all: the promotion is an identity **write** that happens on the *read* path, so it escaped every other consent check — `configureProfile` reads `external_id` unconditionally (only its refresh write was gated), and a `denied` or default-`cookieless` init therefore widened an `identify()`ed email onto the registrable domain, which a non-authoritative seed then never purged back off. The gate is late-bound in `init()` (the controller needs the store, the store needs the layer), so only the consent record — the one value the SDK may write without full consent — is read before it resolves. The `doc` parameter is injectable so tests target other origins via jsdom documents over a shared `CookieJar`.

`createPersistentStore(cookieLayer, maxAgeDays?)` in `persistence.ts` returns a `PersistentStore` (`getItem`/`getItemOrLegacy`/`setItem`/`removeItem`/`crossSubdomain`) layering the cookie over `localStorage`: reads prefer the cookie (the shared source of truth — stale per-origin localStorage must not shadow it), writes go to every available layer (`setItem` returns true only if the value will be readable on the next load: the cookie write must land in cross-subdomain mode, any layer suffices otherwise — but since reads prefer the cookie, a host-only cookie left behind by a *failed* write would shadow the localStorage value with the previous one and report success, so that cookie is removed and reads fall through; failing to remove it is not persistence. Cross-subdomain mode deliberately keeps its stale cookie: reads there have no fallback to drop to, so removing would end identity on every sibling subdomain over one page's failed write); `setItem`'s localStorage write goes through one envelope-typed helper, so the brand stops a bare value reaching either layer. It does **not** read back: the failure that would catch — a Storage shim or extension proxy that no-ops without throwing — is a property of the Storage object, not of a key, so `isStorageAvailable()` verifies it once at startup (it wrote a sentinel and never read it back, which is what let a shimmed store report available) and `local` is null when it fails; a per-write check would put a second `getItem` on the per-event session write for a fact already known, undoing `knownExpiry`'s 2.03 → 1.02 measurement. `removeItem` does read back, being a teardown rather than a hot path, and returns true only when a subsequent read would miss — every consulted layer confirmed the delete, **read-back verified on both**, since `localStorage.removeItem` can no-op without throwing (a Storage shim, an extension proxy) and treating that as success made the teardown boolean lie in the default install, where the cookie layer that does verify is absent — so opt-out/reset can surface a teardown that did not land; methods never throw. Both of `removeItem`'s failure arms (silent no-op, throw) report the same fact at `log.error` through one once-per-key latch, which is **released by the next confirmed removal**: a latch may report once per *episode* but must never outlive the fact it describes, or the next genuine residue for that key is silent — and in cross-subdomain mode, where the return value excludes the localStorage layer, that report is the only signal anywhere that the identifier is still on the device. `writeLocal`'s warn is latched and released the same way, because it sits on the per-event session write, where an unlatched one is a console line per event for the life of the page. Returns `null` only when both layers are unusable.

**Retention.** Every value is stored as `<absolute expiry epoch ms>|<value>` (`encodeStored`/`decodeStored`, in `utils.ts` — see Utilities for why the codec does not live here), and `getItem` deletes (not merely ignores) anything past its deadline **and anything that does not decode** — with one caller-opted exception: `getItemOrLegacy(key)` still removes an undecodable value from the device but returns the bare string instead of null, the migration hook for the consent record (see Tracking Consent); identifiers stay on `getItem`, where a bare value reads as absent. A distinct method rather than an option on `getItem` so the choice is visible in the call — so nothing outlives `maxAgeDays` (default 365, validated as untrusted — including that the day count's millisecond product is finite, since a stamped `Infinity` is an envelope `decodeStored` rejects and every value would be written then deleted on its next read) in *any* mode. In cross-subdomain mode that takes one more move: reads never consult the localStorage mirror `setItem` writes through to, so on a genuine shared-cookie miss (not a read failure) the store sweeps the mirror, once per key per miss episode — without the sweep the mirror sat outside every deadline (an `identify()`ed email, for a visitor the app never re-identifies) and became readable again the moment the integrator turned cross-subdomain off. A throwing sweep un-latches so the next miss retries (as `reconcileTwin` does), and both residue reports — the sweep's and `removeItem`'s — are `log.error`: in cross-subdomain mode the return value excludes the localStorage layer, so a teardown reports success while the identifier stays on the device, and that is the same outcome `clearProfile()` reports at error on the cookie layer. Deleting the undecodable half is what makes that unconditional: a pre-envelope value carries no deadline, so retention can never reach it. Merely ignoring one would strand it — the anonymous ID self-heals (the next mint overwrites the key), but an `identify()`ed `externalId` — routinely an email — is only ever written by `identify()`, so a visitor who upgraded and did not re-identify would have kept theirs forever. Deleted, it leaves the device on the first read and comes back only when the app calls `identify()` again. The deadline is stamped at the **first** write and carried through every later one, so the sliding refreshes elsewhere in the SDK (session activity, `getAnonymousId`'s expiry refresh, the consent record's re-write at init) can no longer extend retention — CNIL's 13-month rule is explicit that a tracker's lifetime must not be automatically extended on new visits, and before this `localStorage` (the default layer) had no expiry at all, so the default install kept identity forever. `setItem` passes the value's *remaining* TTL to the cookie layer so both die together. The carried-forward deadline is **clamped** to `now + maxAgeMs`, so the rule cuts both ways: a refresh cannot extend retention, and *lowering* `maxAgeDays` still reaches existing visitors on their next write — who are the population an integrator tightening retention cares about. To carry a deadline forward it consults a store-local `knownExpiry` map before re-reading storage: `resolveSessionId()` does a read-then-write on every tracked event, and re-reading there doubled the storage reads per event (measured 1.02 → 2.03 `getItem`s/event in the default localStorage-only install). The cache holds **deadlines only** — values are always re-read, which is what `session.ts`'s cross-tab sync relies on — and an entry is never *later* than the deadline on the device — `getItem` caches what it decoded, and `setItem` caches the (clamped) deadline it is about to write, which on a first write is already the shortest a fresh stamp could be; if another tab removes and recreates a key, this tab's cached deadline is the older one and the value gets a shorter life, which is the safe direction. The encoding is the whole stored format: a bare value written by an older build fails to decode, reads as absent and is removed, which is acceptable pre-1.0 and means existing devices mint a fresh anonymous ID once. Acceptable for *identifiers*, that is — the consent key records a refusal, and deleting it unread reverted a recorded `'denied'` to the config seed (the README's own migration advice being `initial: 'granted'`), which is why it alone reads with `getItemOrLegacy`. The Chromium 400-day cap warning is gated on a cookie layer actually being present — hoisting `maxAgeDays` out of the cookie config hoisted that check past its own precondition, so the default (localStorage-only) install warned about a cookie it never writes. `createTrackingConsent` takes the store as an optional trailing parameter; `configureSession`/`configureProfile` take it as a required positional (typed `| undefined`) ahead of the required `isGranted` gate. All three default to a localStorage-only store when it is undefined (internal callers other than `pug.init()`, tests). Restore paths re-write the restored value once per `init()` so a cookie-backed store keeps the cookie present up to the value's deadline (it cannot extend it); the profile's `externalId` refresh is additionally gated on tracking consent (no identity cookie write while denied). The batch queue and the tab registry intentionally stay on raw `localStorage` (origin-local, too chatty/large for a header-bearing channel) — which also puts them **outside** the retention bound, since the deadline rides the store. Neither is a path identity survives a withdrawal on: the registry is cleared by every consent teardown, and the queue by every teardown that *reduces* consent (see the `dropQueue` predicate) — it survives only a transition that reduces nothing: a re-assert of an unchanged cookieless state (identity-free events by construction), or a `'denied'` → `'cookieless'` thaw, where the entry to `'denied'` already emptied it. `reset()` additionally sends-and-drops the queue but leaves the registry (per-tab timestamps, never identifiers, pruned by its own idle timeout). A queue that cannot reach the network is bounded by `batch.maxQueueSize`, not by `maxAgeDays`, and its events carry `sessionId` and `distinctId` (the `externalId` after `identify()`). `pug_device_id` (`DEVICE_ID_KEY`) is outside it too, and unlike those two is cleared by no teardown at all — latent today, since only `push.ts` writes it and push is unexported, but `identify()` reads it. The `maxAgeDays` JSDoc names all three rather than claiming to cover everything on the device. Closing that gap properly means extracting the envelope as a decorator over raw storage so the queue and registry can take it without acquiring a cookie layer — the stated reasons for their bypass are all arguments about the *cookie channel*, none about expiry.

### Tracking Consent (`src/tracking-consent.ts`)

Owns the consent state (`TrackingConsent`: `'granted' | 'denied' | 'cookieless'`). `'cookieless'` is the middle state for GDPR/DPDP reject-analytics-cookies flows: events keep flowing (with `cookieless: true` and no identity — the backend derives a daily-rotating id) while the SDK writes **no identifiers** to the device. The one deliberate exception is the consent record itself under `persist: true` — a strictly-necessary record of the user's refusal, pinned by a case in `cookieless-storage.test.ts` so it stays deliberate and the docs cannot drift from it. The two predicates are **nominally branded** (`GrantedGate` / `TrackingGate`, `(() => boolean) & { readonly __gate: K }`): both are `() => boolean` and are injected positionally into optional parameters, so passing the wrong one compiled silently — and one such swap (`configureProfile` receiving `isTracking`, which re-writes a durable `externalId` to the device in cookieless mode) was invisible to types *and* to all tests, because the guarded branch only runs for a returning visitor who previously called `identify()`. The phantom member is **required**, and all three `isGranted` parameters are positionally required too (and guarded at runtime: each factory throws a `TypeError` at the head on a non-function gate — placed at the head because an unguarded `createCookieLayer` reached `reconcileTwin`'s try with the live twin already expired, destroying its value. `configureSession` assigns `fallbackSessionId` *before* its guard for the same class of reason: thrown first, `resolveSessionId()` returned `''` and every event carried an empty `sessionId`, which the proto's `string.uuid` rule rejects as `InvalidArgument` — classified permanent, so whole batches are committed and dropped. `init()` catches all three and routes them through `reportInitFailure`, which reports a `TypeError` at `log.error` naming it a wiring error rather than at `log.warn` alongside genuine environment failures — otherwise the guards whose whole purpose is to fail loud arrived as a warn that reads like a blocked cookie store while the SDK ran on with no session or profile persistence. A runtime guard still reaches no typed caller, which is why the arity pin covers the compile-time spelling). It was optional "so tests and non-`init()` callers could pass a bare `() => boolean`" — but `src/*.test.ts` is excluded from `tsconfig.typecheck` and vitest transpiles without checking, so tests were never typechecked either way, and there are no non-`init()` production callers. Optionality only let the brand be laundered (`const f: () => boolean = isTracking`, or a `() => isTracking()` wrapper). Making the *parameters* required matters separately: omission was invisible to types, and `mayWriteToDevice()` *defaulted* to permitted when the gate was absent, so an omitted argument silently wrote identity with full permission. It now fails closed (`?? false`) and the head guards throw before any module state is set, so the runtime cost of omission is loud; the type-level pin is what keeps typed callers from ever reaching it. The controller exposes two deliberately different predicates: `isGranted()` (full consent only — gates identity-storage writes, e.g. `configureProfile`'s expiry refresh, `rotate()`/`resetIdentity()`, and the tab registry) and `isTracking()` (granted **or** cookieless — gates automatic listener attachment and answers `isTrackingEnabled()`, but gates *neither* `track()` nor `identify()`: `identify()` requires `isGranted()`, and `track()` branches on `getConsent()` directly because it needs all three states); conflating them is exactly the bug the split prevents. `set(state)` is the general transition (validating, persisting when enabled) and returns a **boolean**; an out-of-domain value **fails closed to `'denied'`** and logs `log.error`, matching the init-time posture rather than keeping the previous state — keeping it meant a CMP passing `'reject'`/`'opt-out'`/`null` left a `'granted'` user fully tracked while `isTrackingEnabled()` confirmed the wrong state. `optIn()` is sugar for `set('granted')`; `optOut()` applies `getRejectState()` — the `onReject` config (`'denied' | 'cookieless'`, default `'denied'`), which lets a banner's reject branch keep identity-free counts without naming `'cookieless'` itself. `onReject` is validated separately from `initial` and cannot be `'granted'` (that would invert the control; it logs `log.error` and falls back to `'denied'`). `setTrackingConsent('denied')` is unaffected — it always means literally denied — so only `optOutTracking()` is redirected. `isPending()` reports whether the user has actually answered (a restored choice or any `set()`, including the fail-closed path) rather than the state being a seed; it backs the public `isConsentPending()`, the consent-banner gate. It is deliberately **not** `isAuthoritative()`, which additionally requires durability because it gates *destroying* identity, whereas `isPending()` only reports. The public `setTrackingConsent(state)` in `pug.ts` wraps `set()` with the transition side effects, consent effects first: re-arm the tab registry on entering `'granted'` (`onConsentGranted()`), or on entering any non-granted state run the identity teardown (`clearProfile()` + `clearSession()`, with the queue drop scoped separately below) — the identity removals are required when leaving `'granted'`, and idempotent in *end state* from any other state though not side-effect-free (they still issue removals, which are cookie deletions in cross-subdomain mode, and may log on an unconfirmed one). The **queue drop is not idempotent-in-effect and is scoped tighter** (`purgePersistedIdentity({ dropQueue })`, with `dropQueue = resolved === 'denied' || wasGranted`): it runs when the transition actually reduces consent — leaving `'granted'` (the consented queue holds identified payloads the user just withdrew consent for) or landing on `'denied'` (a kept cookieless queue would be beaconed by the next pagehide, transmission after a full reject) — and **not** on a re-assert of an unchanged non-granted state, where a CMP restating `'cookieless'` on every load used to destroy the identity-free cookieless queue unsent (the pre-banner `page_view` of every mid-page session, under the cookieless default) while a granted→granted re-assert kept its queue untouched. Both halves are pinned against the real modules in `cookieless-storage.test.ts`; before the granted one existed, making granted→granted run the purge passed the entire suite. Auto-capture reconciles only after the consent effects, matching `init()`'s order — defense in depth now, since no consent-reducing transition arms a tracker, but if the drop predicate ever loosens, purging after `apply()` would destroy the newly-armed tracker's synchronous `page_view`. It aggregates `set()`'s result with the teardown's into the returned boolean, so a failed purge — an identity cookie surviving on the registrable domain — is detectable rather than console-only. Consent-granted-later mints a fresh identity lazily on the next event; pre-consent (cookieless) events are never retroactively linked. `respectGpc` (default false) honors the browser's Global Privacy Control signal (`navigator.globalPrivacyControl`, read once per `init()`; a throwing getter — a privacy extension — logs at `log.warn`, which every install sees, and reads as absent: the signal is an opt-out, so failing to read it must not be silent), resolving it to `getRejectState()`. Precedence is seed → GPC → a choice made on this site: GPC outranks the config seed (it is the user's own standing preference, not the integrator's placeholder) but yields to a restored or explicitly `set()` value, without which an accept click would be re-overridden on the next load and the banner would loop. A GPC-resolved state counts as **decided** (so `isPending()` is false and no banner shows) and as **authoritative** (so `init()` purges identity from an earlier consented visit) — the second is why `isAuthoritative()` is `gpcApplied || (persist && restoredFromStorage)` rather than the storage conjunct alone: GPC is equally durable, being re-asserted by the browser on every load. `respectGpc` without `persist` **warns**: the "a choice on this site outranks GPC" half needs somewhere to record that choice, and without one GPC re-resolves on every load, so `isPending()` stays false (the banner never shows) and a later `optInTracking()` cannot outlive the page — the user is left with no way to accept. The warning fires only when the signal actually resolved consent, so the common `respectGpc: true` + no-GPC-visitor case stays quiet. `createTrackingConsent(projectId, config?, store?)` takes `config: TrackingConsent | { initial?, onReject?, persist?, respectGpc? }`; `initial` is the first-run seed. `TrackingConsent` is **derived** from a `CONSENT_STATES` const array so `isConsent` cannot drift from it: written separately, the predicate still compiled against a widened union while advertising `value is TrackingConsent`, so a new state was un-settable and reported as invalid input. The seed defaults to **`'cookieless'`** rather than `'granted'`: collect, but write nothing to the device until the user has actually answered. `KNOWN_CONSENT_KEYS` is derived from a `satisfies Record<keyof TrackingConsentConfig, true>` map for the same reason `TrackingConsent` is derived from `CONSENT_STATES`: written separately, adding a legal member made valid typed configs fail closed to `'denied'`. **Unrecognized config keys warn and fail closed to `'denied'`** — an unknown key leaves the seed undefined, so it would otherwise fall through to that default silently. TypeScript catches that for npm consumers, but the one-tag install supplies this as untyped `data-options` JSON, which is also what makes the `default`→`initial` rename safe. By default consent is in-memory; with `persist: true` the factory stores opt in/out through the `PersistentStore` (key `__pug_<projectId>_consent__` via `makeStorageKey`; rides the cross-subdomain cookie when active, so an opt-out on one subdomain applies on siblings) and restores any valid persisted value on construction, so it survives reloads. The restore reads with `getItemOrLegacy(key)`: a bare pre-envelope record from an older build is handed back (still removed from the device) rather than deleted unread, `isConsent()` decides whether it was a recorded choice or corruption, and an adopted value flows through the ordinary restore arm — `restoredFromStorage`/`decided` set, so `isAuthoritative()` honors it and `init()`'s identity purge runs for a recorded opt-out — with the refresh write re-enveloping it under a fresh deadline (its original stamp date is unknowable; corruption falls to the existing "invalid, ignoring" warn with the device already clean). `write()` **writes the new value first and then restarts the retention window** (remove + rewrite) when a previous record exists and the value actually changes — the carried-forward deadline is right for every other key, but would leave a user who opted out on day 1 and back in on day 360 with a record lapsing in five days. The previous-record half of the guard (`persistedValue !== null`) exempts the first-ever persist, whose initial write just stamped a fresh window: the restart there was two wasted storage cycles, a spurious "could not clear the previous consent record" on a device with no previous record, and a pointless walk through the one remove-landed-rewrite-failed sequence write-first cannot save. Write-first because this is the one record that must not fail open: removing first meant a remove that landed plus a set that failed left *no* record, and the next `init()` fell back to the config seed — a recorded `'denied'` becoming a more permissive placeholder. A remove that fails logs and keeps the old deadline (early lapse, the safe direction); the narrow remove-landed-then-rewrite-failed sequence logs at error. Guarded on the value differing (tracked in `persistedValue`), or a CMP re-asserting its state would slide the clock on every callback. When storage is unavailable it warns (once per `init()`) and falls back to in-memory. `destroy()` and `reset()` do not clear persisted consent — it is device-level by design. The auto-capture controller stores the desired `autoCapture` selection and gates listener attachment on consent (read through an injected `isTracking` getter, so listeners run in cookieless mode), so `setAutoCapture()` can be called before opt-in and the selection is re-applied on `optInTracking()`. `setAutoCapture()`'s "listeners activate after opt-in" debug message is keyed on `isTracking()` for the same reason — on `isGranted()` it printed in cookieless mode, where they had already activated. When `init()` runs with consent denied it logs a one-time `log.warn`; integrators can detect the state via `isTrackingEnabled()`.

The three public getters answer deliberately different questions before `init()`. `isTrackingEnabled()` ("are events flowing right now?") returns `false`, which is accurate — nothing is being tracked yet. `isConsentPending()` ("has the user chosen yet?") returns `true`, also accurate — no storage has been read. `getTrackingConsent()` ("what state is the SDK acting on?") returns `undefined`, not `'denied'`: a persisted choice is only read from storage inside `createTrackingConsent` during `init()`, so before then the SDK genuinely has no answer, and reporting `'denied'` was indistinguishable from a real opt-out — a consent banner gated on it would re-prompt a user who had already opted in. After `init()` the same trap survives in a second form, which is why `isConsentPending()` exists: `getTrackingConsent()` then reports the state being *acted on*, and before any answer that is the `initial` seed, so a seeded state and a chosen one are the same value (with the `'cookieless'` default, a visitor who has answered nothing and one who chose "reject analytics cookies" read identically). On the CDN path there is a third layer: calls queued before the bundle loads return `undefined` regardless, which is what `ready(cb)` (documented in README) exists to solve.

### Parsers (`src/parsers.ts`)

- `initUserAgentData()` — called during `init()` (and on a consent transition into a tracking state) to asynchronously warm a high-entropy UA cache via `navigator.userAgentData.getHighEntropyValues()`. Gated on `isTracking()`: reading device characteristics for a user who is not tracked at all buys nothing and is itself a device read. Returns void (not a Promise); early events may lack `$osVersion` and `$device` if the promise has not resolved yet. The backend supplements these using the raw UA header.
- `parseUserAgentData()` — synchronously extracts UA Client Hints from `navigator.userAgentData`. Low-entropy props (`$browser`, `$browserVersion`, `$os`, `$mobile`) are read directly; high-entropy props (`$osVersion`, `$device`) come from the cache populated by `initUserAgentData()`. Returns `{}` on browsers without UA-CH support (Firefox, Safari).
- `parseUtmParams(search)` — extracts UTM campaign params from a query string via `URLSearchParams`. Returns only UTM params that are present in the query string with non-empty values: `$utmSource`, `$utmMedium`, `$utmCampaign`, `$utmContent`, `$utmTerm`.

### Session Tracking (`src/session.ts`)

Module-level state, no classes. Sessions are lazily initialized on the first `resolveSessionId()` call and persisted through the `PersistentStore` under a project-namespaced key (`__pug_<projectId>_session__` via `makeStorageKey`), so with cross-subdomain tracking the session (and its `deviceId`) continues across sibling subdomains. Expiry is evaluated lazily on each call — no timers. Cross-tab sync is handled by re-reading storage on every call; if another tab wrote a newer `lastActivityTime`, it is adopted automatically.

- `resolveSessionId()` — called by `pug.track()` on every event. Reads storage on every call (for cross-tab sync), rotates if expired, updates `lastActivityTime`. Persists on every event in origin-scoped mode (localStorage is cheap); in cross-subdomain mode the `lastActivityTime` write is throttled (`ACTIVITY_PERSIST_THROTTLE_MS`, 10s) so the shared cookie is not rewritten on every event — the in-memory state stays exact and session-id changes (`rotate()`/`resetIdentity()`) still persist immediately. The throttle clock (`lastPersistMs`) advances only on a persist that actually lands, so a dropped cookie write leaves it stale and is retried on the next event rather than suppressed for the window. Returns the current session ID.
- `rotate()` — generates a new uuidv7 session ID and writes it to storage immediately (logging a warning if the write does not persist). Exported for users who need to force a new session (e.g. on logout). `resetIdentity()` (session + device reset, on logout) returns a **boolean** and logs an error on a failed persist, since the previous identity could otherwise resurface; both its failure arms log and return rather than throwing, so `reset()` aggregates the return value — a catch-only guard reported success while the previous user's session and device id were still on the device. Both are **gated on consent**: they are public API (`rotate` via the barrel and `STUB_METHODS`, `resetIdentity` via `pug.reset()`) and so reachable while cookieless or denied, where writing a fresh session/device id would plant exactly the identifier those states promise not to store. While not granted, `rotate()` rotates in memory only and `resetIdentity()` clears rather than writes — `reset()` means "forget this user", and in those states there is nothing that should be stored.
- `configureSession(projectId, config, store, isGranted)` — called by `pug.init()`; every parameter is positional and required (`config`/`store` accept `undefined`, the gate does not — a non-function gate throws at the head, uniformly across the three gated factories). Sets `idleTimeoutMinutes` (default 30) and `maxSessionMinutes` (default 1440), adopts the shared `PersistentStore`, and retains `isGranted` at module scope so the later *deliberate* device writes can consult it (`rotate()`, `resetIdentity()`, the tab registry — `resolveSessionId()`'s activity persist is ungated, and is safe only because `track()` branches on consent before reaching it) (contrast `configureProfile`, which only needs it for its init-time refresh). Retaining it is load-bearing: consent became runtime-mutable with `setTrackingConsent`, so gating only at configure time would guard *creation* while leaving `rotate()`, `resetIdentity()` and the registry unguarded.
- `onConsentGranted()` — called by `setTrackingConsent` when entering `'granted'`. Re-arms the tab registry that `configureSession` skipped while consent withheld it, without re-running the "all tabs closed → rotate" heuristic (this tab is demonstrably alive; running it would rotate a live session). Without this the heuristic stayed dead for the page's life, and under the README's recommended consent-first flow — `init()` before the banner is answered — it never armed at all.
- `destroySession()` — a runtime teardown, not a logout: removes the `pagehide` listener, drops this tab's origin-local registry entry, and resets all module state and config to defaults, but leaves the persisted session in place (in cross-subdomain mode removing the shared cookie would end sessions site-wide from one page's teardown), so a later `init()` resumes it. Called by `pug.destroy()`.
- `clearSession()` — removes the persisted session **and the whole tab registry**, detaches the `pagehide` reaper, and clears in-memory state while leaving the module configured, so a later `resolveSessionId()` lazily starts a fresh session. Returns a **boolean** (false when a removal could not be confirmed). Called by `optOutTracking()` and every non-granted transition; in cross-subdomain mode this clears the shared cookie, so the opt-out propagates across sibling subdomains, and logs an error if the removal cannot be confirmed (an unremoved shared cookie would otherwise resurface the identity). Purging the registry is the privacy-teardown case (a device wipe), as opposed to `destroySession()`'s tab teardown which drops only this tab's entry: leaving it behind meant the key survived the purge still carrying the `tabId → timestamp` pair written under granted consent, and the still-attached reaper wrote to the device again on the way out — while the SDK advertised storing nothing.

If no persistence layer is usable, sessions continue in memory only. The tab registry (per-tab heartbeats driving "all tabs closed → rotate on next init") stays on raw `localStorage` and is skipped when `store.crossSubdomain` is true — tab liveness is origin-local, so with a shared session an `init()` on one subdomain with no live tabs there would wrongly rotate a session still active on a sibling; in that mode sessions end by idle/max timeout only. It is also skipped while consent is not fully granted (it is a device write), and re-armed by `onConsentGranted()` if consent arrives mid-page.

### Profile Identity (`src/profile.ts`)

Module-level state, no classes. Manages anonymous profile IDs persisted through the `PersistentStore` under `__pug_<projectId>_profile__` — with cross-subdomain tracking, the anonymous ID and `externalId` ride the shared cookie, so a visitor moving between sibling subdomains keeps one identity. Anonymous IDs are prefixed with `"anon-"` (required by the server for merge operations).

- `configureProfile(projectId, store, isGranted)` — called by `pug.init()` (positional and required, like `configureSession`). Adopts the shared store, sets storage keys, and restores any persisted `externalId` from a previous `identify()` call — **rejecting and removing** one that starts with the reserved `cookieless-` prefix (`RESERVED_DISTINCT_ID_PREFIX` in `utils.ts`, shared with `identify()`'s input check), since a device poisoned by an older SDK would otherwise replay it as `distinctId` forever and have every batch rejected wholesale; mirrors `getAnonymousId()`'s `anon-` validation — and re-writing a valid one to refresh a cookie-backed store's expiry — but only when `isGranted()` (called bare, no fail-open coalesce: the head guard has already rejected a non-function gate), so no identity cookie write happens while consent is denied; the restore-into-memory always happens since it only feeds the consent-gated `track()`/`identify()`).
- `getAnonymousId()` — returns or creates a persistent `"anon-<uuidv7>"` ID (restores from the store when present, refreshing its expiry).
- `resolveDistinctId()` — returns `externalId` if one has been persisted (from a previous `identify()` call, even across page loads), otherwise the anonymous ID. Called by `track()` to set the `distinctId` field on every event.
- `isIdentified()` / `markIdentified(id)` — `isIdentified()` returns `true` when `externalId` is non-empty (derived, no separate flag). `markIdentified` persists the `externalId` so it survives page reloads. Controls whether `anonymousId` is sent on the next `identify()` RPC (first call triggers server-side merge of anonymous → identified profile; subsequent calls skip merge).
- `clearProfile()` — clears storage (both anonymous ID and external ID) and resets identified state, logging an error per key whose removal cannot be confirmed (an unremoved shared cookie would otherwise resurface the identity) and returning a **boolean** so `setTrackingConsent` can surface a teardown that did not land instead of leaving it console-only. Called by `pug.reset()` and every non-granted consent transition.
- `destroyProfile()` — resets all module state but, like `destroySession()`, leaves persisted identity in place (a runtime teardown must not wipe the shared cross-subdomain cookie for every sibling subdomain); `clearProfile()` + `purgeQueue({ send: true })` via `reset()` (or `purgeQueue({ send: false })` + `clearProfile()` + `clearSession()` via `optOutTracking()`) is the deliberate clear. Called by `pug.destroy()`.

`identify(externalId, traits?)` in `pug.ts` sends the `ProfilesSDKService.Identify` RPC via `unaryCall` (see RPC Client) — there is no cached client. On the first call, it includes `anonymousId` so the server merges the anonymous profile into the identified one. Subsequent calls send an empty `anonymousId` (trait-only updates). Respects tracking consent and `dryRun` mode. It requires `isGranted()` (not `isTracking()`), so it drops in cookieless mode — at `log.warn`, once per `init()`, rather than `log.debug`: `isTrackingEnabled()` returns `true` in cookieless, so `if (isTrackingEnabled()) await identify(id)` takes the branch and identifies nobody, and a debug-gated message is invisible to exactly the integrator debugging that. It also rejects an `externalId` starting with the reserved `cookieless-` prefix, which the server uses for derived cookieless identities and enforces with a message-level CEL rule over the whole `BatchCreateRequest` — accepting one would persist it as the `externalId`, making it the `distinctId` on every later event and rejecting every batch containing that user (`InvalidArgument`, classified permanent, so batches are committed and dropped) with nothing pointing back at the `identify()` that caused it.

### Protobuf Codegen (`Makefile`, `proto/`, `src/gen/`, `buf.gen.yaml`)

The SDK's protobuf types are **vendored**, not consumed from a Buf Schema Registry npm package — so consumers `npm install` with no `.npmrc`/registry config and the published package carries the generated code (`dist/gen`, compiled from `src/gen`). Mirrors sdk-android / sdk-flutter; the reusable runtime (`@bufbuild/protobuf`, `uuidv7`) stays as normal npmjs `dependencies`.

- **Provisional pin (release blocker):** `proto/sdk/events/v1/events.proto` is currently hand-patched *ahead* of `PROTO_COMMIT` with the cookieless contract (pug repo branch `feat/cookieless-identity` — `Event.cookieless = 8` + validation restructure); `make protos` generates from the local mirror so `check-codegen` stays green, but before any npm/CDN release the backend branch must merge and the pin must be bumped so `make sync-protos` produces a zero diff (see the RELEASE BLOCKER comment in the Makefile).
- `make sync-protos` — `buf export buf.build/pugsh/pug:$(PROTO_COMMIT)` (read-only download, **pinned** to a specific BSR commit set in the Makefile) into the committed `proto/` mirror, allowlisted (`--path sdk --path common/events/v1 --path common/v1/property_value.proto`) so backend-only trees (`shared/**`, `dashboard/**`, …) are never synced. Bumping protos is deliberate and reviewable: `make proto-latest` prints the newest commit on `main`, then update `PROTO_COMMIT`, re-run `make sync-protos && make protos`, and review the diff. Needs BSR network access; nothing else in the build does.
- `make protos` — `buf generate` (local `protoc-gen-es`, `target=ts`, `import_extension=js`; config in `buf.gen.yaml`) from the committed `proto/` into `src/gen/`, then `node scripts/strip-validate-deps.mjs`, then `make typed-events` (offline, no BSR). `src/gen` compiles with the rest of `src` under the strict tsconfig; google WKTs resolve from `@bufbuild/protobuf/wkt` and are not emitted. `buf/validate` is emitted by `buf generate` (the pug protos import its field-option extensions) but then **stripped**: `strip-validate-deps.mjs` deletes the whole `src/gen/buf/` tree (which holds only `validate/`) and removes `file_buf_validate_validate` from every generated `import` + `fileDesc(...)` deps array. Safe because the SDK no longer validates client-side and `protobuf-es`'s `fileDesc()` rebuilds the descriptor's dependency list from the deps arg (buf.validate is referenced only via field *options*, stored as unknown fields, never as a field type), so `create`/`toBinary`/`fromBinary` stay byte-identical while the ~73 KB `validate_pb` descriptor leaves the bundle (see `src/wire-roundtrip.test.ts`). The strip is deterministic, so `make check-codegen` still passes.
- `make typed-events` — regenerates `src/well-known-events.generated.ts` (a **type-only** file). The script introspects a throwaway compile of `src/gen` (`tsc -p tsconfig.gen.json` → `.codegen-tmp`, gitignored) because node cannot import the `.ts` source directly (protobuf-es enums + `.js`-extension imports). Output is deterministic; CI regenerates and diffs it.

Both `proto/` and `src/gen/` are committed. `@buf/pugsh_pug.bufbuild_es` is **not** a dependency; only `@bufbuild/protoc-gen-es` (a devDependency) + the `buf` CLI are needed, and only to run codegen. The `package.json` `files` allowlist ships `dist` + `pug_sw.js` + README/LICENSE, so `proto/`, `src/`, and the codegen tooling never reach consumers.

### Well-Known Events (`src/well-known-events.ts` + `src/well-known-events.generated.ts`)

`src/well-known-events.generated.ts` is the **type-only** `WellKnownSchemaMap`: a `type` (not a runtime `const`) mapping every web well-known event name string to `typeof <its protobuf *PropertiesSchema>`, imported via `import type` from the vendored `./gen/common/events/v1/*_events_pb.js` (see Protobuf Codegen). Because every import is `import type`, the file compiles to **zero runtime code** — the ~119 event-property schema descriptors are used only for compile-time typing and never reach the browser bundle. The file is generated by `scripts/gen-well-known-events.mjs` (run via `make typed-events`, itself part of `make protos`), which walks every `*PropertiesSchema` exported under the generated `common/events/v1/*_events_pb.js`, reads the wire-name string from the `(common.events.v1.kind)` message option via `getExtension`, and filters by the `(common.events.v1.platforms)` option — events that explicitly target only non-WEB platforms (IOS/ANDROID/DESKTOP/SERVER) are excluded; events without a `platforms` annotation are treated as platform-neutral and included. Proto rather than the SDK is the single source of truth — after `make sync-protos` pulls new schemas, `make protos` re-emits both `src/gen` and this file with no hand-edits.

The same generator pass also emits **`WELL_KNOWN_EVENTS.md`** (repo-root, linked from README) — the human reference listing every web event with its camelCase property names, JS types, and server-side constraints, grouped by proto module (domain). Property names/types come from the compiled schema descriptors (`localName`, scalar/message kind), but the constraints (required / numeric ranges / the `^[A-Z]{3}$` currency pattern) are parsed from the **proto source text**, because `buf.validate` is stripped from `src/gen` (see Protobuf Codegen) and survives only in `proto/`. Both generated artifacts are drift-guarded: `make check-codegen` and CI diff `WELL_KNOWN_EVENTS.md` alongside `src/gen`/`src/well-known-events.generated.ts`, and `src/well-known-events-doc.test.ts` asserts (build-free) that the doc's event list matches the type registry and that README's hand-written domain links match the doc's section headings. It **is** in `package.json`'s `files` allowlist (alongside README), so the README's relative link to it resolves on the npm package page as well as on GitHub.

`src/well-known-events.ts` is the hand-written wrapper: it `import type`s `WellKnownSchemaMap` and derives `WellKnownEventName` (the literal union of all well-known event names) and `WellKnownEventPropsMap` (mapping each name to its `MessageInitShape`) from it. Also defines `TrackEventProps<E>`, `TrackFn`, and `TrackOptions`. `TrackFn` is a **single generic signature** — `<E extends WellKnownEventName | (string & {})>(event: E, props?: TrackEventProps<E>, …)` — resolving props through a conditional type, deliberately *not* two overloads. It was overloads (a narrow well-known one, then an `(event: string, props?: Record<string, JsonValue>)` fallback), which meant a wrong type on a known field never errored: TypeScript abandoned the failed first overload, matched the permissive fallback (a string is a fine `JsonValue`), and the bad payload compiled and shipped to be rejected server-side — the fallback silently absorbed exactly the mistakes the typing existed to catch. One signature leaves nothing to fall through to, so the error lands on the offending property. `(string & {})` preserves editor autocomplete for the well-known literals while still admitting any custom string; plain `string` would absorb the literals and lose completions. `TrackEventProps`'s conditional is **non-distributive** (`[E] extends [WellKnownEventName]`, not a bare `E extends …`): a distributive one expands over the 119-name union whenever `E` is still generic, which is exactly what a wrapper forwarding its own type parameter does — `const forward: TrackFn = (e, p, o) => track(e, p, o)` failed with `TS2590: Expression produces a union type that is too complex to represent`, a compiler resource bailout that names no cause and suggests no fix. Since `TrackFn` is a public export, typing an analytics facade with it is the obvious move, so that path has to work; `TrackEventProps` is exported from the barrel alongside it, being the type consumers need to annotate a props variable. The `E & WellKnownEventName` intersection in the true branch is load-bearing for the same reason and reads even more like a no-op: the tuple guard alone constrains `E` enough that `WellKnownEventPropsMap[E]` is legal, but the bare form expands the indexed access eagerly and reintroduces TS2590 at the same call shape. The two are not independently pinned — removing *only* the tuple still typechecks, because the intersection alone defers the expansion; `track-types.test-d.ts` catches the fully-reverted form, not either half. Props resolve to `Record<string, PropValue>` (`JsonValue | bigint | Date`) rather than `Record<string, JsonValue>`, mirroring what `jsValueToPropertyValue` accepts at runtime: protobuf-es maps proto `int64` to `bigint`, so under a bare `JsonValue` bag the int64 fields on five well-known events (`file_uploaded`, `file_downloaded`, `export_completed`, `chat_attachment_uploaded`, `chat_attachment_downloaded`) were **unwritable in every spelling** — `number` failed the message shape and `bigint` failed the index signature. The old permissive overload had absorbed that silently; removing it turned it into a hard error, which is why `track-types.test-d.ts` now carries an int64 case. `scripts/gen-well-known-events.mjs` maps the 64-bit scalars (ScalarType 3/4/6/16/18) to `bigint` so `WELL_KNOWN_EVENTS.md` stops documenting them as `number`. Guarded by `src/track-types.test-d.ts` (see Type-level tests), which pins both wrapper forms. The `TrackFn` change itself is compile-time only and does not alter the CDN bundle (though other changes in the same release may). Re-exports `JsonValue` from `@bufbuild/protobuf`. All of this is **compile-time only** — there is no runtime well-known/custom distinction; both route through the same heuristic in `track.ts`.

### Event Creation (`src/track.ts`)

`toEvent(projectId, kind, identity, props?, opts?)` builds a protobuf `Event` object from event kind, identity, properties, and options. `identity` is the `EventIdentity` union — either `{ cookieless: true }` (the server derives identity; the ids are omitted from the wire entirely, which edition-2023 explicit presence makes distinguishable from a sent-empty string — the proto's `string.uuid` rule rejects an empty `session_id`; `distinct_id` carries no field rule and is covered instead by the message-level `event.identity_required_unless_cookieless`) or `{ sessionId, distinctId }`. Each arm carries `?: never` members for the other's fields, which is what actually closes the union: with no shared property TypeScript has no discriminant, and excess-property checking against a union admits any property present in *any* constituent — so every spelling of a cookieless event carrying identity compiled, including the spread and variable forms an explicit literal tag would still admit. The runtime branch tests `identity.cookieless === true` rather than `'cookieless' in identity`, so it agrees with the type instead of silently accepting `{ cookieless: false }` and emitting `cookieless: true` for it. Each call generates a fresh `eventId` (uuidv7, required by the proto) and stamps `occurTime` with the current time (or `opts.timestamp` if finite). The `customProperties` field is a typed `map<string, common.v1.PropertyValue>` — a oneof over `string`, `int64` (TypeScript `bigint`), `double`, `bool`, and `Timestamp`.

**There is one runtime path for all events.** Well-known event names are a compile-time typing affordance only (see Well-Known Events); at runtime `toEvent` does not consult any schema, so well-known and custom events populate `customProperties` identically via `jsValueToPropertyValue` on every entry in `props`. Mapping: `string` → `stringValue` (truncated to 1024 UTF-8 bytes with a warn log if longer — proto's `string.max_len = 1024` is enforced server-side as a code-point count, so byte-truncation is strictly more conservative); `boolean` → `boolValue`; finite `number` → `intValue` if `Number.isSafeInteger` else `doubleValue` (non-finite numbers dropped); `bigint` → `intValue`; `Date` → `timestampValue` via `timestampFromMs(d.getTime())` (`Date(NaN)` dropped); arrays/objects → `JSON.stringify` then string policy (circular structures and `toJSON` returning undefined dropped); `null`/`undefined` dropped silently (no warn — they're common and unactionable). Every other drop is logged at the call site with the property key for grep-ability, since `track()` itself never throws and undiagnosed drops would mask real user bugs.

Note the int-vs-double consequence: a whole-number value on a proto `double` field (e.g. `purchase.amount = 5`) now serializes as `intValue` (the heuristic keys off the JS value, not the schema). This is safe because the backend stores custom properties in a ClickHouse `Map(String, Variant(String, Int64, Float64, Bool, DateTime64(3)))` and every numeric read coalesces the `Int64` and `Float64` variant slots to `Float64`; safe integers are exact in both, so aggregations/filters are unaffected. Dropping the runtime schema removed the former `validateWellKnownProps`/`isWellKnownEvent`/`buildKnownPropertyMap`/`scalarToPropertyValue`/`reflect()` machinery.

Auto properties include: `$projectId`, `$url`, `$referrer`, `$locale`, `$screenWidth`, `$screenHeight`, `$sdkVersion`, UA Client Hints when available (`$browser`, `$browserVersion`, `$os`, `$osVersion`, `$device`, `$mobile`), and any present UTM params. `$pageTitle` is sent on `page_view` **only** (`eventPageView`, defined in `track.ts` rather than `events/page_view.ts` so a core module does not import a tracker one — when it did, `pug.test.ts`'s `vi.mock` of that module broke `track()` on the missing export). Titles routinely carry names and order numbers, so riding every click, scroll and frustration event multiplied the exposure for no added signal; the events that follow on a page share its `sessionId`, so the title is still joinable. `sessionId` and `distinctId` are set as top-level fields on the `Event` proto (their own ClickHouse columns), not properties. `distinctId` is the profile identifier — `externalId` after `identify()`, otherwise the anonymous ID. `toEvent` drops an event if `create(EventSchema, …)` throws (structurally invalid) or if `beforeSend` drops it; field-constraint validation is left to the server.

`beforeSend` (`configureBeforeSend`, from `init({ beforeSend })`) is the single privacy hook — it **replaced `sanitizeUrl`**, which was removed rather than deprecated (pre-1.0, and two overlapping hooks is worse than one break). `toEvent` builds both property bags as plain JS, runs the hook, then converts via `mapPropsViaHeuristic`. Return the event, `null` to drop, or `undefined` to keep in-place mutations — `undefined` can't mean "drop" because mutable bags invite forgetting the return. The `BeforeSendEvent` handed to the hook is **held in a `draft` const and reused** as the `undefined` fallback, not rebuilt from `applyBeforeSend`'s arguments: rebuilt, a hook that *replaced* a bag (`e.autoProperties = mask(e.autoProperties)`) and fell off the end had its redaction discarded and the raw original sent — the one direction a privacy hook must never fail, and one nothing warned about. Both bags are also `readonly` on the type so that spelling is a compile error first (pinned by `before-send-types.test-d.ts`; the runtime honors it either way). `autoProperties` is typed `Record<string, string>` — every value it holds is a string, and the `PropValue` it used to carry made the README's own `maskUrl(event.autoProperties.$url)` a `TS2345`. `$projectId`/`$platform`/`$sdkVersion` are re-asserted from a snapshot taken *before* the call: the hook gets the live bag, so a `delete` would empty what a naive re-assert reads back. A throw or malformed return drops the whole event (no narrower fallback than a URL field has), each warning one-shot but on **its own flag** — shared, a throw at page load silenced every later malformed return for the life of the page. `isPlainBag` rejects anything whose prototype is not `Object.prototype`/`null`: a `Map`, `Set`, array or class instance yields nothing from `Object.entries`, so accepting one shipped an event stripped to its three re-asserted properties, silently. Only the throw path logs, and only the error's *type*. `sessionId`/`distinctId` are not exposed. A one-tag install can't supply a working hook (`data-options` is JSON, which holds no functions) but the key is *not* filtered — `autoInitFromScript` spreads `data-options` wholesale — and a non-function value fails closed to dropping **every** event. `$url`/`$referrer` (in `toEvent`) and `form.action` (in `form.ts`) pass through `scrubUrl` first, so the hook receives values with known-sensitive query/fragment params already redacted; structural masking (IDs in paths, whole URLs) remains its job, which is the migration cost of dropping `sanitizeUrl`. That cost is invisible to JS and one-tag installs, which get no compile error, so `init()` warns when it sees a stale `sanitizeUrl` key. Re-exports `TrackFn`, `TrackEventProps`, `TrackOptions`, `JsonValue`, `PropValue`, `WellKnownEventName`, and `WellKnownEventPropsMap` from `well-known-events.ts`, and defines `BeforeSendEvent`/`BeforeSendFn`.

### Transport Layer (`src/transport.ts`)

`createTransport(endpoint, apiKey)` returns an object with `send`, `sendBatch`, and `beacon` methods. `send`/`sendBatch` call `unaryCall` (see RPC Client) for the `BatchCreate` RPC using the vendored generated code in `src/gen` (see Protobuf Codegen). The `beacon` method uses `navigator.sendBeacon` with binary protobuf for reliable delivery during page unload; since `sendBeacon` cannot carry request headers, the API key is appended as a `?api_key=` query parameter on the beacon URL (the same Connect-protocol wire format `unaryCall` posts).

### RPC Client (`src/rpc.ts`)

`unaryCall(endpoint, apiKey, method, message, timeoutMs?)` is a hand-rolled Connect-protocol (binary) unary client built on `fetch` — it replaces `@connectrpc/connect-web` to shrink the bundle. Given a generated unary method descriptor (e.g. `EventsService.method.batchCreate`), it POSTs `toBinary(method.input, message)` to `{endpoint}/{service.typeName}/{method.name}` with `content-type: application/proto`, `connect-protocol-version: 1`, and the `x-api-key` header, then parses the response via `fromBinary(method.output, …)`. All three RPCs (`BatchCreate`, `Identify`, `Subscribe`) go through it. A 5s default timeout is enforced with an `AbortController`. Server rejections, network drops and timeouts throw `RpcError` (exported), which carries a **numeric** gRPC status code: rejections use the code from the Connect JSON error body, while drops and timeouts surface as transient codes (`unavailable`/`deadline_exceeded`) so the batch layer retries them. Deliberately not *every* failure: a 2xx body that is not protobuf and a `toBinary` bug surface raw, which `batch.ts` (non-`RpcError` → permanent) drops rather than retries forever. `RpcError` replaces `@connectrpc/connect`'s `ConnectError` for the batch layer's permanent-vs-transient classification.

### Batching Layer (`src/batch.ts`)

`createBatchedTransport(endpoint, apiKey, projectId, partialConfig?: BatchOptions)` is the main transport factory. `BatchOptions` is `{ readonly [K in keyof BatchConfig]?: BatchConfig[K] | undefined }` — a mapped type rather than `Partial<BatchConfig>`, whose members reject the `T | undefined` config-builder spelling under `exactOptionalPropertyTypes` (pinned in `init-options.test-d.ts`), and mapped rather than hand-written so a fourth knob cannot be settable on `BatchConfig` while unsettable through `init({ batch })`. Members are read individually by `validated(name: keyof BatchConfig)` rather than spread, since spreading an explicit `undefined` would replace the default with it. Each member's `kind` and `min` come from `BATCH_RULES`, a `satisfies Record<keyof BatchConfig, …>` table — the `KNOWN_CONSENT_KEYS` pattern, and it closes the one asymmetry the mapped type leaves: `BatchOptions` makes a fourth knob *settable*, but nothing made it *validated*, so it could ship unchecked. Passing kind and min per call also let them be mismatched — `validated('maxWaitMs', 'whole', 0)` (rounding a `setTimeout` duration that is fine fractional) and `validated('maxSize', 'finite', 0)` (admitting the `lock(0)`-forever config the floor exists to reject) both compiled. `validated` treats each member as **untrusted** (`typeof`/`Number.isFinite`/`>= min`), not just absent-or-not: the one-tag install supplies `batch` as `data-options` JSON, where a bare `value >= min` accepted `Infinity` (what `JSON.parse` gives for `1e999`, which disabled the `maxQueueSize` bound and size-triggered flushing outright) and `null` (`null >= 0` is true, and `setTimeout(fn, null)` fires immediately, collapsing batching to one request per event). The two event counts are additionally rounded down to whole numbers (`kind: 'whole'`; `maxWaitMs` is `'finite'`, a `setTimeout` duration being fine fractional). A fractional `maxSize` had `lock()` reserve half an event — `slice` returns `[]` while `locked` keeps the `0.5`, and a flush releases only the queues that returned events, so that queue stayed locked for the life of the page (measured at `maxSize: 1.5`: 18 send attempts, not one carrying a cookieless event). Rounded down rather than replaced by the default, which for `maxQueueSize` would answer a too-tight bound (1.5 → 1) by widening it 1000x; `lock()` truncates its own limit as well, so the invariant does not rest on the config path alone. It creates the inner RPC transport, validates/merges batch config with defaults, and wraps everything in a batched transport that:

- `purgeQueue({ send })` empties both queues and returns `{ ok, destroyed }` (the exported `PurgeResult`, reused by `purgeQueuedEvents` in pug.ts so the aggregate cannot be re-spelled narrower there) — `ok` answers "did the queues leave the device", `destroyed` is how many events that cost. `purgeQueuedEvents` in `pug.ts` warns on it — every consent teardown, not just `init()`'s non-authoritative branch, since the page that queued them promised a retry at warn level wherever the break happens — gated on a non-zero count so the no-op purge every other load performs stays silent, and on `send: false`, since `reset()` beacons them out rather than destroying them. `destroyed` counts **per queue** what actually left the device (a queue whose key survived destroyed nothing; the memory-only cookieless queue always did), which a single `ok && total` could not express: `ok` is structurally the localStorage queue's answer alone, so gating on it made a real cookieless loss unreportable. It **includes** each queue's in-flight locked batch, which `purge()` discards too (counting `size` instead made the warning silent in exactly the highest-loss case) but which may still be delivered — and a failed consented purge destroys the un-persisted debounced tail while counting 0 for the surviving key, so the number is approximate in both directions, never an audit. `send` decides whether what is queued gets one last beacon first. **True only for `reset()`** — a logout, where consent is unchanged and those events were agreed to. Every consent teardown passes false: transmitting after the user chose Reject is a fresh act of processing on data they just withdrew, and Art. 7(3) protects the *prior* collection, not a later send. Its `false` means exactly one thing — a queue key survived on the device — and the queue's own `purge()` reports it at `log.error` with the consequence spelled out, for the silent no-op and the throw alike (the failure mechanism does not pick the level). A dropped farewell beacon reports through `reportBeaconLoss` but does not flip the return: beacons fail routinely under content blockers, so folding delivery in made `reset()` read as a failed teardown on verifiably clean devices — and the README recipe shows that boolean to end users as "identity may remain". The farewell report is held until **after** both purges and marked *terminal* only when the consented purge actually landed: `terminal` asserts the events are gone, which only the purge knows. Announced beforehand it printed "dropped unsent — the queue is removed" one line above `purge()`'s own "may be sent on a later visit" — the second being the true one, since a surviving key really does hydrate and send on the next `init()`. Claiming destruction is the wrong direction for a privacy-relevant message, and it is the same contradiction `purgeQueuedEvents` avoids by keying on `destroyed`. When the purge lands, the message still says the events were dropped unsent rather than the other phases' "will retry on next init()", which is false exactly there. `purgeQueuedEvents({ send })` in `pug.ts` adds no message about the *failure* — a surviving queue key is reported by the queue's own `purge()` with the cause in hand, and a dropped farewell beacon by `reportBeaconLoss`; anything here would guess at both. It does warn about the *destruction*, keyed on `destroyed > 0` and `send: false`: a purge that discards nothing is the common case and `reset()` beacons first, while a purge that could not remove the persisted key destroyed nothing there — those events hydrate and send on the next `init()`, so claiming destruction would contradict, at a lower level, the error `purge()` logged one line earlier saying they may still be sent. The message says the events *may* include identified payloads rather than asserting it, since on the ordinary `'cookieless'` → `'denied'` transition every one of them is identity-free. The reason it gives is what the events are — identified payloads from an earlier granted visit — not "consent forbids a queue", which is false under the `'cookieless'` default.
- Buffers events in a queue storage (localStorage-backed with in-memory fallback). **Cookieless events route to a second, memory-only queue** (`storageFor` picks by `event.cookieless`): persisting their payloads would itself be device storage, which cookieless mode promises not to do. Both queues share the flush state machine (one in-flight batch), and **every** send path — `flush()`, `beaconFlush()` and `destroy()` — builds a single batch drawn from both queues, committing or rolling back only the queues that contributed. Only `flush()` caps at `maxSize` (and reserves part of that budget for the cookieless queue whenever it has events waiting, so a consented backlog of ≥`maxSize` cannot starve it — the reserve is floored on the *cookieless* side, and when the two floors cannot both fit, i.e. `maxSize: 1`, the queues **alternate** across flushes. Flooring only the consented side made that floor the entire budget at `maxSize: 1`, a legal config and the natural one for per-event delivery, so cookieless got `lock(0)` forever); `beaconFlush()`/`destroy()` fully drain, since there may be no second chance to send. Selecting one queue per flush instead starved the cookieless queue for the entire duration of any continuous consented stream (`storage.size > 0` always chose `storage`) while `totalSize() >= maxSize` counted the stalled backlog and tripped the threshold on every arriving event, degrading consented traffic from batched sends to one request per event; because `storage` is localStorage-backed, a single transiently-failing consented event survived page loads and could block cookieless collection on that device indefinitely. A hard-killed tab can still lose whatever the cookieless queue holds — bounded by `maxQueueSize`, **not** by `maxWaitMs`, which bounds only the happy path: a transient failure rolls the batch back and retries indefinitely (measured at 60s with `maxWaitMs: 50`). The transient-retry test in `batch.test.ts` pins the *storage silence*, not the bound. `destroy()`'s beacon-failure path logs the two outcomes at different levels — consented events remain in the persisted queue (`log.warn`, recoverable on the next `init()`), cookieless events are gone with the memory-only queue (`log.error`, permanent) — since `beacon()` returns false whenever `sendBeacon` is absent or blocked, not only on payload rejection. Recoverability is judged by the queue implementation chosen at creation, never a storage probe at report time (a probe that healed after creation promised recovery from a memory queue dying with the page), and the page-hide failure paths `sync()` the 1s persist debounce to disk before reporting, so "remain in the persisted queue" is true for the freshest events — the click that triggered the navigation.
- Flushes when batch size is reached (`maxSize`, default 10) or timer expires (`maxWaitMs`, default 5s)
- Uses `sendBeacon` on `visibilitychange`/`pagehide` for reliable delivery during navigation
- Classifies errors as permanent (non-`RpcError`, or `RpcError` with gRPC codes 3/5/6/7/9/12/16) vs transient (retry via rollback, only for `RpcError` with retryable codes)
- Has a 3-state lifecycle: `idle` → `flushing` → `idle`, or any → `destroyed`. If destroyed while flushing, the in-flight request completes normally but no further flushes are scheduled.
- Supports `immediate` flag to attempt direct send for priority events, falling back to the queue on transient errors

The queue storage implementations share a common shape with a two-phase lock/commit/rollback protocol: `lock(n)` reserves events for sending, `commit()` removes them on success, `rollback()` unreserves on failure. Two implementations: `createMemoryQueueStorage` (in-memory) and `createLocalStorageQueueStorage` (persists across page loads with debounced writes).

### Push Notifications (`src/push.ts`, `pug_sw.js`)

Push is an optional, tree-shakeable module — `pug.ts` never imports it, so non-push users pay zero bundle cost. **Currently unexported (deferred feature):** push is planned for a later phase, so `index.ts` does not re-export it and the CDN bundle/snippet do not expose it — the code stays in-tree and compiling, but `dist/push.js` is unreachable via the exports map. Re-add the barrel line, the `cdn.ts` api entries, and the snippet method names (via `STUB_METHODS` in `cdn-install.ts` — the `satisfies` in `cdn.ts` and the snippet fixture test enforce the rest) when the feature ships. Three regressions to re-check then: add the push methods to `INIT_INDEPENDENT_METHODS` in `cdn-install.ts` (they work without init() and must not be counted as "will be dropped" by the before-init warning); queued promise rejections (the dispatch closure already logs them — keep that guard); and `pug_device_id`, which `subscribePush` writes to raw `localStorage` with no expiry and no teardown clears. It needs the `PersistentStore` (so retention covers it) plus removal in `reset()` and the consent teardowns, or it is a durable device identifier surviving an opt-out.

**`src/push.ts`** exports three functions:

- `subscribePush(vapidPublicKey, options)` — registers the service worker at `options.swPath` (default `/pug_sw.js`), waits for it to become active, subscribes via VAPID, generates/retrieves a persistent `deviceId` from `localStorage` (`pug_device_id`), and calls `DevicesService.Subscribe`. Requires `options.endpoint` and `options.apiKey` (same values passed to `init()`). Does not read pug's internal state.
- `unsubscribePush(options?)` — unsubscribes the push subscription from `pushManager`.
- `setupNotificationClickTracking(track)` — sets up `notification_clicked` tracking across two cases: (1) page already open: listens for a `pug_notification_click` postMessage from the SW; (2) page opened by the click: reads `?pug_nc=<JSON>` from the URL, calls `track`, strips the param with `history.replaceState`. Returns a cleanup function.

**`pug_sw.js`** (project root, copy to public dir) — drop-in service worker. Handles `install`/`activate`/`push`/`notificationclick`. On `notificationclick`: if a page is open, sends a postMessage to the first matched window (which is then focused); if no page is open, opens `targetUrl?pug_nc=<data>` so `setupNotificationClickTracking` can read it on load.

### CDN Distribution (`src/cdn.ts`, `src/cdn-install.ts`, `scripts/build-cdn.mjs`)

The SDK also ships as a self-contained IIFE for script-tag installs: `scripts/build-cdn.mjs` (plain node — `npm publish` runs `prepublishOnly` under node, not bun) bundles `src/cdn.ts` with esbuild into `dist/cdn/pug.min.js` (+ sourcemap with sources inlined — the readable form, since `src/` is not shipped), prints gzip size + SRI hash, and **fails the build over the size budget** (`GZIP_BUDGET_KB` in the script, 45; ~42.5 KB gzip today — raising it is a deliberate, reviewable change). The bundle lives under `dist/cdn/` because tsc emits `dist/pug.js` from `src/pug.ts` — a root-level bundle would overwrite that module and break the ESM package. package.json's `jsdelivr`/`unpkg` fields still point at it (keeping jsDelivr a `<script>` fallback; `npm install`/bundler users resolve via `exports`/`main` and are unaffected either way), but the documented `<script>` installs now load it from the first-party CDN at `cdn.pugs.dev/vX.Y.Z/pug.min.js` — an `@`-free, version-in-path URL, because a `pkg@version` in a customer's HTML matches Cloudflare Email Address Obfuscation and gets rewritten to `[email protected]`, breaking the URL. `scripts/publish-cdn.mjs` uploads the bundle to R2 on release; `npm publish` still ships the package (see `RELEASING.md`).

`src/cdn.ts` is the side-effectful entry (deliberately **not** exported from `index.ts` — importing the SDK stays side-effect-free; only executing the bundle installs the global). It builds the full public API object plus a CDN-only `ready(cb)` (runs `cb` post-load; the documented way to read getters or chain promises, since queued calls return `undefined`) and `version` (= `SDK_VERSION`), then delegates to `src/cdn-install.ts`:

- `installPug(w, api)` — mutates the loader-snippet stub **in place** (object identity survives, so early-captured references stay live), drains `_q` preserving array identity, and overrides `queue.push` so stub methods captured pre-load dispatch live afterwards. Guards: `__loaded` already set → duplicate script load (GTM double-fire, SPA re-mount), warn + no-op, first install wins; `window.pug` without a `_q` array → foreign global (e.g. the pug template engine), warn + never clobber.
- `replayQueue(pending, dispatch, initialized)` — strict FIFO with per-call try/catch (a throwing queued `init('')` must not kill the rest). **No init-hoisting**: reordering would change consent semantics (autocapture page view firing before a queued `optOutTracking`). Emits one aggregate warning for calls queued before the first `init` — docs tell integrators to start denied via the `trackingConsent` init option, never a queued pre-init `optOutTracking()`.
- `autoInitFromScript(script, init)` — the one-tag install (`data-project-id`/`data-api-key` required, `data-endpoint`, `data-options` JSON with flat attributes winning). **Fails closed** on any malformed input (never init with half a privacy config). Runs before replay when no queued `init` exists (so queued calls land after init); a queued `init` always wins. Inert under GTM/eval (no `document.currentScript`).

The canonical loader snippet lives in `README.md`; `src/cdn-install.test.ts` extracts it, executes it against fakes, and asserts `examples/cdn/index.html` embeds a byte-identical copy (only its `src` differs). Load-bearing snippet details: stub shape `{ _q, _v: 1 }`, the method list (single-sourced as `STUB_METHODS` in `cdn-install.ts`, which the `cdn.ts` api object `satisfies` — add a method in one place and the compiler + fixture test flag the others), the 1,000-entry queue cap (bounds memory when the bundle is blocked; inert after load since live dispatch keeps the queue empty), the `s.onerror` console breadcrumb, and the foreign-`window.pug` guard — `if (w.pug)` bails, but warns `[Pug SDK] …` when the existing global is *not* our stub (no `_q`), so a foreign global (e.g. the pug template engine) fails loud like installPug's matching guard while a re-run over our own stub returns silently. Snippet URLs pin exact versions pre-1.0 — the fixture test asserts every doc-pinned `cdn.pugs.dev/vX.Y.Z` equals `package.json`'s version, so a forgotten bump fails CI; at 1.0 the docs switch to a rolling major alias (`cdn.pugs.dev/v1/`). Manual harness: `examples/cdn/index.html` (build, `bun run serve`, open `/examples/cdn/`).

### Logging (`src/logger.ts`)

`log.warn`/`log.error` always write; `log.debug` is gated behind a module-level flag that is off by default and set by `init()` from the `debug` init option (`setDebugLogging`), then reset by `destroy()`. Gating matters because the SDK runs inside a host application's console: an ungated debug channel narrates every event for every customer forever. `warn`/`error` stay ungated — they report things an integrator must see (rejected batches, bad config, a `track()` before `init()`, an event too malformed to encode) without first knowing a flag exists, so the flag can only widen what is visible, never narrow it. That asymmetry is worth stating precisely in the public docs: the `debug` option governs the *consent-denied* and *dryRun* drops, not every drop, and an earlier draft of its JSDoc listed the pre-init drop among them — which is `log.warn` and therefore unreachable by a flag `init()` sets. Every write goes through `safeConsole`, which swallows a throwing/absent console so the never-throw guarantees hold. Note the gate lives in the real module, so any test that `vi.mock`s `./logger.js` bypasses it entirely — `src/logger.test.ts` covers the gate directly, and mock factories must include `setDebugLogging` for modules that import it (`pug.ts`), or `init()` throws on the missing export.

### Utilities (`src/utils.ts`)

- `makeStorageKey(projectId, name)` — generates a namespaced localStorage key.
- `isCaptureSuppressed(el)` — true when `el` or an ancestor carries `data-pug-no-capture`.
- `getSafeElementText(el, maxLength)` — the element's **direct child text nodes only**, whitespace-collapsed and truncated (trailing whitespace the cut exposes is dropped); `''` when capture is suppressed or the text is user input — a `<textarea>`, or anything under a `contenteditable` ancestor. The `contenteditable` check resolves **inheritance** (`closest('[contenteditable]')`, honoring a nested `contenteditable="false"` island): reading the attribute off the click target alone caught only a bare `<div contenteditable>text</div>` and missed every real editor, which puts the attribute on a root while the pointer lands on the `<p>`/`<span>` holding the typed text — so a draft shipped as `click.text`. Deliberately not `HTMLElement.isContentEditable`, which resolves inheritance natively but is `undefined` in jsdom, making any guard built on it untestable here. Replaces `innerText`, which returned the whole subtree: a click target is often a wrapper rather than the leaf under the pointer, so clicking a card sent every name, email and total it wrapped, and a `data-pug-no-capture` marker on the sensitive leaf never ran because the read happened at the ancestor. The old tests could not see this — jsdom does not implement `innerText`, so they stubbed it with `Object.defineProperty` and asserted against a fake that had no subtree semantics at all.
- `scrubUrl(url)` / `configureUrlRedaction(params?)` — replaces the values of known-sensitive query **and fragment** params (`token`, `access_token`, `code`, `email`, `password`, … — case-insensitive, plus any key ending `_token` while the default list is active; a replacement list is exact-match by name, still case-insensitive, being the integrator's own statement) with `redacted`, applied to `$url`/`$referrer` in `toEvent` and to `form.action` in `form.ts` **before** `beforeSend` runs, so the hook adds masking rather than being the only thing between a reset token and the backend. Non-string input passes through untouched: `form.action` is element-typed when a form control is named `action` (named-property shadowing on `HTMLFormElement`), and the guard's `includes` probes sit outside the try, so the leading `typeof` check is what keeps the never-throws promise. The fragment matters on its own: an OAuth implicit-flow `#access_token=…` is never sent to a server *except* through analytics, since it is part of `location.href`. A fragment is redacted when it has a `?` (a hash route's query — redact after the `?`) or contains an `=` (a bare implicit-flow fragment); anything else carries no params. It is deliberately **not** additionally gated on the fragment being free of `/`: that read a slash as "this is a route, not a query", but `#access_token=…&state=/dashboard` and `…&redirect_uri=https://…` are the ordinary shape of an OIDC callback, so the guard disabled redaction in precisely the case the fragment handling exists for. Nothing is lost by dropping it, because `redactQuery` already returns null when no key matched, so a genuine hash route (`#/orders/42`, `#section`, `#/search/q=shoes/page=2`) comes back byte-identical through the same path. `redactQuery` and `redactFragment` share one "unchanged" protocol (null), so `scrubUrl` has a single comparison rather than one null-check and one string-equality check. `redactQuery` iterates `params.keys()` live rather than over an `Array.from` copy: `set()` on the key at the cursor replaces that pair in place and only ever splices away *later* duplicates of the same name, so no distinct key is skipped (fuzzed against a copying implementation over 50k query strings, 0 divergences). Unchanged URLs are returned byte-identical rather than re-encoded (though a URL that *is* redacted gets its whole query re-serialized by `URLSearchParams`, normalizing untouched pairs too — documented in README for anyone joining `$url` against server logs). A URL that does not parse (no base is used — the three inputs are always absolute) **fails closed** through `scrubOpaque`: the same matchers run over the sliced query/fragment at the string level, since the reachable funnel is a malformed `form.action` — when the browser cannot parse the attribute it hands back the raw attribute text, template bugs and live reset tokens included — and this is the one privacy control that otherwise failed toward leaking. A no-match unparseable input still returns byte-identical through the shared null protocol. `init({ redactUrlParams })` replaces the list or disables it with `false`; an **empty array warns and falls back to the default list**, since an empty `Set` is truthy and matches nothing, so `[]` disabled redaction exactly like `false` but silently — which `userList.filter(...)` coming up empty reaches without anyone meaning to. Validation lives in `pug.ts` because `utils.ts` deliberately imports nothing — adding `import { log }` there broke every suite that `vi.mock`s `./logger.js`, since the hoisted factory then runs before its own spies are initialized.
- `encodeStored(value, expiresAt)` / `decodeStored(raw)` — the `<absolute expiry epoch ms>|<value>` retention envelope every persisted value is wrapped in (see Retention). `encodeStored` returns the nominally-branded `StoredEnvelope` (`string & { __envelope }`), which `CookieLayer.set` requires — enveloped and bare values are otherwise the same `string`, and a bare value written through the cookie layer reads as undecodable and is deleted by the store's next `getItem`; the brand makes that seam a compile error (pinned in `cross-subdomain-types.test-d.ts`). Reads stay unbranded: what comes off the device is not trustworthy enough to carry it. Lives here, not in `persistence.ts` which owns the layering, for the import-freedom reason above: the storage-asserting suites each hand-rolled the format, and importing the codec from `persistence.ts` drags `logger.js` into them and trips the same hoisting trap.
- `DEFAULT_MAX_AGE_DAYS` (365) / `SECONDS_PER_DAY` — the retention default and its unit conversion, used by `persistence.ts`, which owns retention. `cookie.ts` needs neither: every cookie write now states a lifetime the store computed, and the twin migration reads its own out of the value's envelope.
- `safeStringify(value)` — `JSON.stringify` for log interpolation of untrusted values, falling back to `String()` (and to a literal placeholder if even that throws). The validators interpolate the very values they reject, and those (bigint, circular refs, a throwing `toJSON`) are exactly what makes `JSON.stringify` itself throw — out of `createTrackingConsent` (the one factory `init()` calls unguarded) and out of `set()`, which the public `setTrackingConsent` reaches. Used at every untrusted interpolation site in `tracking-consent.ts`, `persistence.ts` (`resolveMaxAgeMs`, where the throw previously downgraded the whole SDK to memory-only persistence behind a generic catch) and `pug.ts`.
- `urlBase64ToUint8Array(base64String)` — converts a VAPID public key from base64url to `Uint8Array<ArrayBuffer>` for `pushManager.subscribe()`.
- `isStorageAvailable()` — probes localStorage by writing a **per-call token** under a **per-call key**, **reading it back**, then removing it (best-effort, in a `finally`). The read-back is what catches a Storage shim or extension proxy that no-ops `setItem` without throwing. The per-call **key** stops two tabs probing a shared name concurrently from clobbering each other and both downgrading a working store to memory-only; the per-call **token** stops residue reading back as this run's own write. Residue is bounded by `strandedProbeKey`, **not** by the sweep: on a store whose `removeItem` never lands, a fresh key per probe strands a new one every call (~2–3 per `init()`, accumulating across visits, outside the retention envelope and every teardown) and the sweep cannot reclaim any of them, since it removes through that same failing `removeItem`. So the key this tab already stranded is reused until a removal lands — one key, overwritten in place. The sweep is the complementary half: it reclaims keys an *earlier* failure stranded once the store recovers, taking only demonstrably stale ones (judged from the timestamp each key carries) so another tab's in-flight probe is never touched. Reuse cannot collide across tabs, since each minted its own key before stranding it. Only the write is verified — a removal that no-ops is narrower (values still persist) and `PersistentStore.removeItem` checks that one per call, so failing the whole layer on it would cost the default install its session and anonymous ID on every load. Returns `true` if available, `false` if blocked (private mode, quota, security policy). Used by `persistence.ts`, `session.ts` (tab registry), `batch.ts`, and `push.ts`.

### Key Patterns

- Trackers receive a `track` function and call it directly — they do not access the transport. All browser event listeners are attached globally (document/window level) during `init()` and removed during `destroy()`.
- Use `const = () =>` arrow functions everywhere. The only exceptions are `function` expressions that need `this` binding (e.g., history method wrappers in `page_view.ts`).
- Events are protobuf `Event` objects created via `toEvent()`, not plain JS objects.

### Design Invariants

- **`track()` must never throw.** It is wrapped in a centralized try/catch (with defensive logging via the internal `log` module) and any transport errors are caught via `.catch()`. Because trackers call `track()` from places like monkey-patched `history.pushState`/`replaceState`, an exception would break the host application. Callers may rely on `track()` being safe to call without their own error handling.
- **`identify()` must never throw.** Like `track()`, it is wrapped in a centralized try/catch; invalid input, calls before `init()`, denied consent, `dryRun`, and RPC failures are logged and the returned promise resolves without sending. Callers may `await` it without their own error handling.
